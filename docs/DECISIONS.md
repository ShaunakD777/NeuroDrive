### ADR-001 — Python core with a browser-based viewer
- **Status:** accepted (2026-10-10)
- **Context:** The user is most comfortable in Python and wants to understand the core. The three
  linked views need rich interactivity (clickable neurons, scrubbing, live charts).
- **Decision:** All simulation, maths and learning in Python (`src/neurodrive`). A FastAPI server
  exposes REST and WebSocket APIs. A Vite + React + TypeScript app renders the three views.
- **Alternatives:** (a) everything in TypeScript in the browser: simplest linking, but the core
  would not be in Python; (b) Python desktop UI (PySide6 + pyqtgraph, or Dear PyGui): one
  language, but weaker interactive visuals, harder to verify automatically, harder to share;
  (c) pygame + matplotlib: weak for linked inspection.
- **Consequences:** a client/server boundary (message schemas, generated TS types). Replay data
  is sent once and scrubbed locally. Claude Code writes the web code; the user focuses on Python.

### ADR-002 — 2D top-down simulation
- **Status:** accepted · **Decision:** 2D Canvas rendering. **Alternative:** 3D (as in the reference
  video). **Why:** 3D adds no learning value and much effort; 2D shows rays, trails and populations
  more clearly.

### ADR-003 — Own kinematic physics (with a grip limit) instead of a physics engine
- **Status:** accepted (2026-10-10, revised)
- **Context:** Cars must respond believably to steering and throttle. General physics engines (Box2D, pymunk) simulate rigid bodies: collisions, contact forces, friction and momentum. In NeuroDrive, touching a wall ends the episode and cars never interact, so most of an engine would go unused. Neither engine includes a car model, so car-like steering would still have to be written on top.
- **Decision:** Our own kinematic bicycle model, fixed dt = 1/30 s (ARCHITECTURE §6.3), applied to all cars at once as NumPy arrays. It includes a grip limit: sideways acceleration v²/R is capped at a_lat_max = 9 m/s², so at high speed the car cannot turn tightly and runs wide. This makes braking before corners necessary, which gives the throttle output a real job.
- **Alternatives:** (a) Box2D / pymunk: steps bodies one by one through Python bindings (too slow for GA/RL populations), adds solver details that make exact replay harder to guarantee, and hides the maths behind a library; (b) ready-made environments such as Gymnasium CarRacing: pixel observations instead of rays, a fixed track and reward, and it conflicts with the observation contract and the linked views.
- **Consequences:** deterministic, vectorised, fast and fully explainable; grip and steering limits are config values that can change in robustness studies (task 12.2). No skidding, drifting or car-to-car contact. Revisit with a physics v2 (our own dynamic bicycle model with tyre slip) if drifting is wanted. Car-to-car interaction would be the only strong reason to reconsider an engine.

### ADR-004 — Continuous actions: any value from −1 to +1, produced by tanh
- **Status:** accepted (2026-10-10, revised)
- **Context:** Steering and throttle must be graded (a gentle left, half throttle, light braking), not just on/off.
- **Decision:** Both outputs are continuous numbers anywhere between −1 and +1. The output layer uses tanh, which smoothly maps any weighted sum z into that range: z = 0 → 0, z = 0.2 → 0.197, z = 0.5 → 0.462, z = 1 → 0.762, z = −1 → −0.762. It only gets close to ±1 when z is beyond about ±3, and never reaches it exactly. Steer: −1 full left, 0 straight, +1 full right, values between are proportional (−0.3 = 30 % of full left lock). Throttle: +1 full acceleration, 0 coast, −1 full braking, values between are proportional.
- **Alternatives:** (a) discrete actions (left/straight/right): coarse, turns control into classification; (b) sigmoid rescaled as 2·sigmoid(z) − 1: mathematically the same as tanh(z/2), so no benefit; (c) linear output with clipping: outputs can grow without limit and the gradient becomes zero once clipped.
- **Consequences:** matches the reference video and works for imitation (regression), evolution and Gaussian policy-gradient RL (the tanh output is the mean of the Gaussian, and the sampled action is clipped). Untrained networks drive roughly straight. The environment still clips actions to [−1, 1]. Watch for saturation: large weighted sums push outputs near ±1, which gives all-or-nothing "bang-bang" driving and near-zero gradients (slope 1 − 0.99² ≈ 0.02). The exam's smoothness metric measures this.

### ADR-007 — Run storage: plain folders (master copy) + SQLite mirror
- **Status:** accepted (2026-10-10, revised; supersedes the files-only version)
- **Context:** While learning, runs must be easy to open and read by hand. Later (large comparisons, the final report, dashboards) we need to query across many runs, e.g. "median held-out exam score of all GA runs with mutation rate 0.05".
- **Decision:** Two stores with separate roles. (1) Run folders (YAML, JSON, JSON-lines, .npz; ARCHITECTURE §6.13) are the master copy and are written first. (2) The SQLite database `runs/neurodrive.db` is a mirror built from the folders, with tables `runs`, `metrics` (one row per metric value), `checkpoints` (including a weights BLOB copy), `exams`, `exam_episodes` and `studies`. The Runner updates the mirror after each unit, with WAL mode so the server can read while training writes. `nd db rebuild` regenerates the database from the folders and `nd db check` reports differences. If they disagree, the folders win. It uses Python's built-in `sqlite3`: no new dependency, no ORM, readable SQL.
- **Alternatives:** (a) folders only: cross-run queries are slow and manual; (b) SQLite only: opaque while learning, and one bug could corrupt everything; (c) MLflow / Weights & Biases: an extra service that hides the structure.
- **Consequences:** a new module `experiment/db.py` and a new task 5.5b. Tests must show that a database rebuilt from the folders matches the one written step by step. Because `runs/` is git-ignored, the database stays out of git.

### ADR-014 — Version control on GitHub, with a secret-free repository
- **Status:** accepted (2026-10-10)
- **Context:** The user wants a versioned history on GitHub, with a saved version at the end of every stage. The repository must always be safe to publish: no secrets, API keys, tokens, private keys or personal data.
- **Decision:** One GitHub repository. Work for each phase happens on a branch `phase-<N>-<short-name>`; every verified task is one small commit; when a phase is complete it is merged into `main` and tagged `phase-<N>` (the "version" of that stage), then pushed after the user confirms. `main` always holds the last completed phase, with all tests passing. Secret safety is layered: (1) the project needs no secrets, and any future one is read only from environment variables, with a `.env` file that is git-ignored and a committed `.env.example` containing placeholders; (2) `.gitignore` excludes `.env*` (except the example), keys, certificates, `runs/`, databases, recordings, `node_modules/` and build output; (3) pre-commit hooks run gitleaks (secret scanning), private-key detection and a large-file check before every commit; (4) GitHub Actions CI repeats the secret scan plus lint and tests on every push; (5) GitHub secret scanning and push protection are switched on in the repository settings where available; (6) Claude Code is denied reading `.env` files.
- **Alternatives:** (a) commit straight to `main`: simpler, but an unfinished phase would break the "last good version"; (b) tags only, without phase branches: fine for a solo project, but harder to abandon a failed approach; (c) relying only on `.gitignore`: does not catch a key pasted into source code.
- **Consequences:** a new task 0.6 (pre-commit, CI, first push). Claude Code stages files by name after checking `git status`, never uses `git add -A` or `git add .`, never force-pushes, and never rewrites history that has been pushed. If a secret is ever committed, it must be treated as leaked: revoke it first, then clean the history.


### ADR-015 — The web dev server forwards `/api` and `/ws` to the Python server
- **Status:** accepted (2026-10-12)
- **Context:** The browser loads the page from the Vite dev server (port 5173) but the Python server listens on port 8000. A browser treats these as two different origins and blocks REST calls between them unless the Python server explicitly allows it (CORS). Task 0.3 left this question open.
- **Decision:** In development, Vite forwards every request under `/api` and `/ws` to `127.0.0.1:8000` (configured only in `web/vite.config.ts`). The browser talks to a single origin, and the web app builds its WebSocket address from the page's own address. The Python server needs no CORS configuration.
- **Alternatives:** (a) enable CORS in `server/app.py`: also works, but adds server configuration that must stay in step with the web app's address and loosens what the server accepts; (b) hard-code `localhost:8000` in the web app: couples the web code to one development setup.
- **Consequences:** `nd serve` must be running for `/api` and `/ws` to work in development (Vite logs a proxy error when it is not). If the app is ever served by the Python server itself, no web code changes are needed because the addresses are already relative. Reversible: removing the proxy and adding CORS touches only `vite.config.ts` and `server/app.py`.

### ADR-016 — api v1.1: the `health` and `hello` message shapes are part of the contract
- **Status:** accepted (2026-10-12)
- **Context:** ARCHITECTURE §7 (api v1) named `GET health` and the `hello` message but did not define their fields. Tasks 0.3 and 0.4 built them, and task 0.5 wrote the built shapes into §7. The user asked for that addition to be treated as a contract change.
- **Decision:** `GET /api/health` returns `{status: "ok", version}` and `/ws/live` sends `{type: "hello", version, api}` first on connect, where `version` is the NeuroDrive package version and `api` the message-contract version. The API version becomes **v1.1** (`API_VERSION` in `server/schemas.py`). Versioning rule for the API from now on: adding a message or a field bumps the minor number (v1.1 → v1.2); removing or changing the meaning of a field bumps the major number (v1 → v2).
- **Alternatives:** (a) keep "v1" because nothing has been released yet: simpler, but the version would stop being a reliable record of what the contract says; (b) jump to v2: overstates an additive change.
- **Consequences:** the web app can compare `hello.api` with the version it was built for. The generated TypeScript types are unchanged (`api` stays a string).

### ADR-017 — Views as pages, with a companion drawer and a layout switch
- **Status:** accepted (2026-10-12)
- **Context:** Task 0.4 put the three views (Environment, Network, Experiment) side by side as resizable panels. Even as placeholders they felt crowded, and the real content (a track canvas, a network diagram, charts) needs more room. But the project's core teaching moment is seeing a car and its network change together (§8.2 linking), which pure pages would hide.
- **Decision:** By default each view is a full page with its own address, switched with tabs. Each page has a collapsible companion drawer that shows a compact version of a linked view. A layout switch offers Page (default), Split (any two views) and All (the three panels). The selection store and the live connection live at app level, so selections survive page changes. Built as task 0.4b.
- **Alternatives:** (a) plain pages with a split option: simplest, but car and network are not visible together by default; (b) task-based workspaces ("Drive & inspect", "Network deep-dive", "Experiments"): strongest for teaching, but the most layout code and less obvious naming; (c) keep the panels with a full-screen "focus" button: smallest change, still crowded by default.
- **Consequences:** a new task 0.4b before 0.6. Later view tasks (1.8, 1.9, 2.7) also provide the compact companion version of their view. The Playwright smoke test changes from "three panels" to "pages, drawer and layouts".

### ADR-018 — api v1.2: live-session messages (column-array frames, track geometry over REST, one session per connection)
- **Status:** accepted (2026-10-15)
- **Context:** ARCHITECTURE §7 named the `/ws/live` messages but not their fields. Task 1.7 builds the live session, so the shapes must be fixed, and ADR-016 says adding messages bumps the API minor version.
- **Decision:** (1) A `frame` carries the cars as **column arrays** (`x`, `y`, `psi`, `v`, `alive`, `progress`, `status`, `action`: one entry per car), plus `selected` (rays in metres and the 7-number observation of the selected car, or null). (2) The `scenario` message does **not** carry track geometry; the browser gets it from `GET /api/tracks/{name}` (and the names from `GET /api/tracks`). (3) Each WebSocket connection owns **its own session**; it ends when the connection closes. Messages: client to server `load_scenario {track, policy, n_cars, seed}`, `play`, `pause`, `step`, `set_speed {speed}`, `reset`, `select_car {index}`, `key_state {steer, throttle}`; server to client `hello`, `scenario`, `frame`, `episode_end`, `error`. `set_param` is added with task 1.9. The API version becomes **v1.2**. The server steps the world in fixed 1/30 s physics steps; the speed factor changes how many steps are taken per second, never the step size; while playing, one frame is sent per max(1, speed) steps, i.e. at most 30 per second on average. Wire numbers are rounded (positions and speeds to 3 decimals, angles to 4).
- **Alternatives:** (a) a list of car objects per frame: easier to read, about twice the size, clumsier to loop over; to be revisited if readability matters more than size. (b) track geometry inside `scenario`: one message instead of two requests, but the geometry is resent on every scenario load. (c) one shared global session: allows spectators, but needs locking and a rule for who drives.
- **Consequences:** the browser makes a REST call for the track before drawing. The generated TypeScript types grow (every message and the track models). The track folder is fixed to the repository's `tracks/` folder (no environment variable). A live session is not recorded yet, so a live drive cannot be replayed until a later task adds that.

### ADR-019 — api v1.3: the neuron driver, `set_param`, the neuron readout and activation curves
- **Status:** accepted (2026-10-16)
- **Context:** ADR-018 said `set_param` would arrive with task 1.9, which builds the one-neuron driver and its view. The browser must show the neuron's inputs, weighted sum and output, and let the user change the weights live, without ever computing network outputs itself (ADR-012).
- **Decision:** (1) A new `neuron` policy choice. All cars of a scenario share one neuron: steer = f(w_left * d_left + w_right * d_right + bias), with d_left and d_right the far-left (+60 degrees) and far-right (-60 degrees) ray readings (observation entries 0 and 4), and a fixed throttle. It starts with all weights and the bias at 0 and a throttle of 0.15. (2) One command `set_param {name, value}`, where `name` is `w_left`, `w_right`, `bias`, `throttle` or `activation`; the value is a number, or one of tanh, sigmoid, relu, linear for `activation`. Weights and bias are limited to +-30 and the throttle to [-1, 1]; anything else is an `error`. The server answers with a frame. (3) `frame.selected` gains `neuron`: the selected car's inputs, which rays they are, weights, bias, each input's contribution (weight times input), the weighted sum z, the output, the activation and the throttle, all computed by Python. (4) `GET /api/activations` returns z values from -5 to 5 with the four activation functions sampled on them, so the browser can draw the activation curve without computing it. The API version becomes **v1.3**.
- **Alternatives:** (a) the browser recomputes z and the activation for instant slider feedback: smoother, but it breaks ADR-012 and the display could disagree with the car; (b) separate typed commands such as `set_weight` and `set_activation`: stricter, but more messages than the one name the contract lists; (c) start with weights that already steer: removes the experiment of finding them, which is task 1.10's job.
- **Consequences:** a slider drag shows its effect after one round trip to the server (about one frame). The generated TypeScript types grow. Per-car neurons and richer networks arrive with Phase 2 and extend `selected` then.

### ADR-020 — The neuron driver's settings last for the whole live session
- **Status:** accepted (2026-10-18)
- **Context:** ADR-019 created a fresh all-zero neuron on every `load_scenario`. Reset already kept the weights, but changing the number of cars, the start, the track or the driver wiped them, and so did a server restart. The user asked for the weights and settings to stay put.
- **Decision:** each live session keeps one neuron. It starts at zeros (as before) and keeps its weights, bias, activation and throttle through `reset` and every `load_scenario`, including a detour through another driver. The browser remembers the settings it last saw in a neuron readout and, after a reconnect (a new session), sends them back with `set_param`. No message or field changes, so the API stays **v1.3**.
- **Alternatives:** (a) keep the settings only through `reset` (the old behaviour): wipes hand-tuned weights on any scenario change; (b) store the settings on the server across sessions: two browser tabs would then fight over one neuron; (c) also keep them across a page reload with browser storage: not asked for, possible later.
- **Consequences:** a reloaded page still starts from zeros. Saving and loading named settings (for example `configs/baselines/hand_neuron.yaml`) would be a later feature.

### ADR-021 — Local secret scan with detect-secrets, run through Python; gitleaks stays in CI
- **Status:** accepted (2026-10-18)
- **Context:** ADR-014 put gitleaks in the pre-commit hooks. Windows Smart App Control now blocks the compiled `gitleaks.exe` that pre-commit builds ([WinError 4551]), so every commit was refused. The `python -m` workaround used for the private-key hook cannot help, because gitleaks is not a Python program. Task 0.6 named "run that check in CI instead" as the fallback, which would leave no secret scan before a commit.
- **Decision:** the local secret scan is detect-secrets (v1.5.0, Yelp), a Python scanner, started as `python -m detect_secrets.pre_commit_hook` with a baseline file `.secrets.baseline` (no findings in the repository today). Lock files and the generated TypeScript types are excluded, as their hashes look like secrets. gitleaks keeps scanning the whole history in CI on every push, and GitHub push protection stays on.
- **Alternatives:** (a) rebuild the gitleaks hook: a large download, and Smart App Control may block the new program too; (b) gitleaks in CI only: no secret scan before a commit; (c) turn Smart App Control off: Windows cannot turn it back on without a reinstall.
- **Consequences:** two scanners with different rules guard different stages. Checked when installed: the hook flags a planted fake GitHub token and AWS key, and passes on every file in the repository. If detect-secrets ever reports a harmless string, it is reviewed and recorded in `.secrets.baseline`, never skipped.

### ADR-022 — Per-track time limit: 2 laps at an average of 16 m/s
- **Status:** accepted (2026-10-18)
- **Context:** the time limit was a fixed 90 s (ARCHITECTURE §6.6, Driving Exam v1), chosen for the 731 m `train_loop_01`. The half-size Monza tracks (task 1.11) are 2,900 m a lap; 2 laps in 90 s would need 64 m/s, over twice the top speed. A time limit is needed so that episodes end, costs stay bounded and faster driving scores better, but its value only has to be fair to the track.
- **Decision:** time limit = ceil(target laps × lap length / 16 m/s), in whole seconds (`env/world.py`: `time_limit_for`, `WorldConfig.for_track`). 16 m/s is a little over half the 30 m/s top speed. It gives 92 s on `train_loop_01` and 363 s on Monza. The Driving Exam v1 and the live server use it; a bare `WorldConfig()` keeps 90 s, so existing tests and the recorded Study S1 (run at 90 s) are unchanged.
- **Alternatives:** (a) one fixed limit long enough for every track (for example 400 s): a car could crawl round the short loop and still pass; (b) a limit per track written into each track file: a track contract change, and every new track needs a hand-chosen number; (c) a time limit set by a reference driver's lap time: depends on a driver that does not exist yet.
- **Consequences:** `train_loop_01` gets 2 more seconds than before (92 s versus 90 s). Lap times stay comparable within a track, not across tracks. Fitness v1's time bonus (time limit − finish time) grows with the track, which is fine while fitness is compared on one track at a time.


### ADR-023 — api v1.4: the `random_networks` policy
- **Status:** accepted (2026-10-19)
- **Context:** task 2.6 puts multilayer networks in the live session: the roadmap's scenario "20 random networks, seed selectable". ADR-016 says adding to the message contract bumps the API minor version.
- **Decision:** (1) `load_scenario.policy` and `scenario.policy` gain the value `random_networks`: car i is driven by its own [7, 16, 16, 2] network with Xavier-initialised weights, zero biases and tanh everywhere. (2) The networks come from the scenario `seed` (seed 0 when it is null), through the child stream named "init" of the seed's generator, so a seed always gives the same drivers. The same seed also keeps its old meaning of a seeded random start; with no seed every car starts on the start line, so differences between cars come only from their networks. (3) The networks are built when the scenario loads and kept through `reset`. (4) No new message or field: the frame is unchanged (`selected.neuron` is null for this policy). Sending each car's network trace to the browser is left to task 2.7. The API version becomes **v1.4**.
- **Alternatives:** (a) a separate `network_seed` field: lets starts and brains vary independently, but adds a field and a UI control for little gain now; (b) a policy where all cars share one random network: that is `MLPPolicy`, useful for training but not for showing "random brains differ"; (c) rebuild the networks on every `reset`: the same result for a given seed, but loses the chance to keep edited networks later.
- **Consequences:** the generated TypeScript types and the driver dropdown gain one value. A seeded start and the brains are tied to one number, so they cannot be varied separately until a later task adds a field.


### ADR-024 — api v1.5: the `network` message and `selected.trace`
- **Status:** accepted (2026-10-19)
- **Context:** task 2.7 draws the selected car's multilayer network in the browser. ADR-012 says the browser never computes network outputs, so the server must send every number: the weights and the values of the forward pass. ADR-019 had already said richer networks would extend `selected` in Phase 2. The roadmap lists frame size as a risk.
- **Decision:** (1) A new server message `network {car, layer_sizes, activations, weights, biases}` carries one car's weights and biases (rounded to 4 decimals). It is sent after `scenario` when a scenario loads and again after each `select_car`, because the weights do not change while driving. (2) `frame.selected` gains `trace {activations, weighted_sums}`: the selected car's forward pass on its current observation (rounded to 4 decimals; 0.6 KB per frame, measured), so the diagram's input circles hold exactly the observation. It is null for the other drivers. (3) The server computes the trace on demand for the current observation (`trace_of` on the policy) instead of reusing the trace of the last `act` call, which belongs to the previous step. (4) The Network view shows the diagram for the `random_networks` driver and keeps the Neuron view for the others. The API version becomes **v1.5**.
- **Alternatives:** (a) repeat the weights in every frame: simpler, but the weights are 3.3 KB (measured) and a 20-car frame is 1.4 KB, so every frame would be about 3.4 times larger for numbers that never change; (b) send the weights over a REST call: needs the session's networks to be reachable by id, which live sessions do not have yet; (c) send the whole population's traces in every frame: 20 times the data for something only the selected car's view needs.
- **Consequences:** a client must keep the latest `network` message and match its `car` to `frame.selected.index` (the diagram waits for the matching pair). The generated TypeScript types grow by two models. When learning changes weights during a drive (later phases), a new message or a periodic resend will be needed; this ADR covers fixed networks only.


### ADR-025 — api v1.6: live explanations in the frame and a `what_if` command (instead of REST for now)
- **Status:** accepted (2026-10-19, chosen by the user from three options)
- **Context:** task 2.10 needs, for the selected car, the contributions and sensitivity of its outputs (task 2.9) and the network's answer for a changed observation (what-if). The roadmap and ARCHITECTURE §7 named a REST route `POST explain/forward {network ref, observation}`, but a live car's network has no reference: it lives inside one WebSocket session (ADR-018, ADR-024).
- **Decision:** (1) Every frame of the random-networks driver carries `selected.explain`: both outputs' receipts and the 2 × 7 sensitivity table for the selected car's current observation (measured: 0.8 KB of a 2.8 KB 20-car frame; the whole frame takes about 0.4 ms to build). (2) A new WebSocket command `what_if {observation}` (paused only) is answered with an `explanation` message computed from the car's exact, unrounded weights, including the real outputs now and the sensitivity's straight-line prediction, so the browser does no maths (ADR-012). (3) `POST explain/forward` is deferred to Phase 5, when checkpoints give networks a real reference (run + unit). The API version becomes **v1.6**.
- **Alternatives:** (B) a stateless REST route with the weights sent back by the browser: matches the roadmap's route, but the weights it has are rounded to 4 decimals, so a what-if at the current observation would not equal what the car does (about 1e-3 off), and 3.3 KB travels with every slider move; (C) a REST route that reaches live sessions by id: exact, but needs shared global session state and locking, which ADR-018 avoided.
- **Consequences:** the roadmap's file `server/app.py` is not changed in task 2.10. What-if works only while paused (a moving car's observation changes 30 times a second, so a question about it would be stale at once). Phase 5 adds the REST route for checkpoints next to this command.


### ADR-026 — api v1.7: the what-if ghost car, and `what_if` sends only the changed inputs
- **Status:** accepted (2026-10-19, follow-up to task 2.10 at the user's request)
- **Context:** ARCHITECTURE §8.2 says that dragging a what-if slider shows a ghost car with the alternative action. The browser may not simulate (ADR-012), so the motion must come from Python. Also, `what_if` (ADR-025) sent the whole observation as the browser had it, rounded to 4 decimals, so even "unchanged" inputs differed slightly from the car's real ones.
- **Decision:** (1) Every `explanation` carries `ghost`: the server runs `env/car.step_cars` for 2 s (60 steps) from the selected car's pose, as two cars in one batch, one holding the network's real action and one the what-if action (both clipped to [-1, 1]); it sends both paths and their end poses. Only the car physics runs: no crash, track or progress rules. (2) The look-ahead is 2 s: at the slow speeds of random brains (about 2 m/s) 1 s left the ghost under the real car. (3) `what_if` now sends `overrides {index: value}` instead of the full observation; the server applies them to the car's exact observation, so `{}` gives exactly the car's real output. The real and what-if actions are both computed by the same `forward` call, so equal inputs give equal bits. (4) The Network page's car switcher gains a drop-down of every car. The API version becomes **v1.7**.
- **Alternatives:** (a) let the ghost re-run the network at every step (closed loop): truer to driving, but the what-if question is about one changed observation, which no longer holds after the first step; (b) a longer look-ahead such as 3 s: clearer at low speed but a held action drifts further from what the network would really do; (c) keep sending the full observation and snap values within rounding of the real ones: works, but hides the rounding rather than removing it.
- **Consequences:** a ghost path can leave the road (the world's crash rule is not applied), which the legend explains as "held actions only". The what-if command is not backward compatible with v1.6 (`observation` is rejected); the browser and the generated types change together.


### ADR-027 — api v1.8: the decision trail and looking back at an earlier step
- **Status:** accepted (2026-10-20, task 2.11; options chosen by the user: A1 + B1)
- **Context:** ARCHITECTURE §8.2 asks for a trail behind the selected car, coloured by the selected output, and for clicking a trail point to "jump to that step" and show the network trace then. The browser may not compute traces (ADR-012), and a live session so far kept no history.
- **Decision:** (1) **Look, do not rewind (A1):** clicking a trail point or dragging "Look back" (paused only) sends `inspect_step {step}`; the server answers with `moment`: the car's pose, rays, observation and action at that step, and its network's trace and explanation recomputed from the stored observation by the same functions a frame uses. The simulation stays at its current step; Step, Play, another car or a new scenario returns the views to now. (2) **Memory (B1):** the session remembers the last 60 s (1,800 steps) of every car's pose, speed, observation (full precision), action and running flag in fixed-size arrays (step t in row t mod 1,800), about 3.8 MB for 20 cars and 19 MB for 100. (3) **Trail on the wire:** each frame's `selected.trail` carries the selected car's new points (one per step taken since the last frame); after a load, a reset or `select_car` it carries every remembered point with `replace: true`. Only steps at which the car was still running are listed. `scenario.trail_seconds` tells the browser how much to keep. (4) The API version becomes **v1.8**.
- **Alternatives:** (A2) rewind the world by re-simulating from step 0 to t (it is deterministic): a truer jump, but slow late in a long drive, it throws away the future and the what-if ghost and frames would need rework; (B2) the whole episode for the selected car only: tiny, but a newly selected car has no trail; (B3) the whole episode for every car: up to about 100 MB for 100 cars on Monza; a separate `trail` message instead of a frame field: cleaner to read but would change the message sequence every existing client and test relies on.
- **Consequences:** a trail point older than 60 s cannot be inspected (the slider starts at the oldest remembered step). The HUD kept showing the present while an earlier step was looked at (changed by ADR-028); the Network view, the drawer, the inspector and the rays show the earlier step, with a banner and "Back to now". What-if is unavailable while looking back (it asks about the present). The neuron driver's readout is not part of a moment, because its settings may have changed since.

### ADR-037 — Learner contract v1, run folder v1 and runner v1: saved state, budgets, exams at checkpoints, exact resume (task 5.5)
- **Status:** accepted (2026-11-02, chosen by the user: decisions 1A, 2A, 3A, 4A of the task 5.5 Brief)
- **Context:** driving methods from 5.7 on train for minutes to hours; a killed run must continue exactly, studies compare methods at equal budgets, and the timeline (5.9) replays examined checkpoints. Learner v0, run folder v0 and runner v0 (ADR-030) had no saved state, no budgets other than a unit count, and no exams.
- **Decision:** (1A) a learner's state is named NumPy arrays plus a small JSON `info` (counters and every random generator's state), stored together with the runner's unit, totals and clocks in `state/latest.npz` (no pickle; `allow_pickle=False`). Learner v1 adds this as the optional `Resumable` protocol (`state()`, `restore()`); a learner without it trains but cannot resume. (2A) The state is saved after every unit, last in the unit's order (train → metrics line → checkpoint and exam → state), keeping only the latest and replacing it atomically (temporary file, then rename). Resume cuts the folder back to the state's unit (later metrics lines, checkpoints, exam cards and a half-written temporary state are removed) and continues; runs with status running (killed) or failed can be resumed. (3A) Every checkpoint of the schedule 0, 1, 2, 5, 10, 20, 50, … (plus the last unit) is examined when exams are on and the network drives; exam time is recorded as `exam_wall_clock_s` and kept out of the training clock and budget. (4A) Resume is the Python function `runner.resume(learner, store)`; the toy learner stays without saved state; `nd resume --run <folder>` arrives in 5.7 with random search, the first resumable method. Budgets: `Budget(units, env_steps, wall_clock_s)`, any limit stops the run after the unit that reaches it (overshoot at most one unit); meta.json records `budget`, `exams`, `stop_reason`, `resumed_at`. Run folder version 1; version-0 folders are still read.
- **Alternatives:** (1B) pickle the learner: no work per learner, but opaque, fragile across code changes, and unsafe to load from shared folders; (2B) state only at checkpoints: a late crash could lose hundreds of units; (2C) keep every state: disk grows with run length; (3B) exams every N units: too sparse early or too costly late; (3C) only the final checkpoint: nothing to replay along the way; (4B) also make the toy learner resumable now (optimizer moments, minibatch position, `nd resume`): about twice the scope for runs that take seconds.
- **Consequences:** resumed runs equal uninterrupted ones except for wall-clock times (tested by killing a separate process with `os._exit` at four moments). Toy runs keep their Phase 4 numbers and now write version-1 folders with a units budget and exams off. Every new learner that should survive a crash must implement `state()`/`restore()` and save every generator it draws from.

### ADR-038 — The SQLite mirror as built: db v1, a mirror that never stops a run, no `studies` table yet (task 5.5b)
- **Status:** accepted (2026-11-02; D1 and D2 chosen by the user: the recommendations A, A)
- **Context:** ADR-007 fixed the two stores (run folders as master copy, `runs/neurodrive.db` as a rebuildable mirror) and the tables. Building it raised questions ADR-007 does not answer: what happens to a training run when the database cannot be written, what fills the `studies` table when run folders record no study, how the runner keeps the mirror in step across kills and resumes, and whether database time counts against a wall-clock budget.
- **Decision:** (D1A) A mirror that cannot be written (locked for more than 5 s, disk full, a database of another schema version, a value SQLite cannot hold) gives one `RuntimeWarning` and stops mirroring that run; the run itself goes on. `nd db check` shows the gap and `nd db rebuild` repairs it. (D2A) No `studies` table yet: `runs` has a `sweep` column, and the `studies` table arrives in 5.10 together with a `study` field in meta.json. Implementation: schema db v1 in `PRAGMA user_version`, tables `runs`, `metrics` (one row per value; booleans 0/1; a list `x` becomes `x[0]`, `x[1]`, …), `checkpoints` (with the `.npz` bytes), `exams`, `exam_episodes`; WAL mode with `synchronous=NORMAL`; the runner writes the folder first, then one transaction per unit (`Mirror.add_unit`), and re-copies the whole run from its folder when it starts and when it resumes (`Mirror.sync_run`), so a kill between the folder and the database is repaired on resume; a checkpoint or exam card saved again replaces its row, as the file is replaced. Database time is measured and kept out of the training clock, like exam time (ADR-037). The wall-clock limit is now compared with the training time recorded in the last metrics line (like the step totals), not with the clock after that unit's checkpoint and state writes, so a run stops after the first unit whose line reaches the limit. `nd exam` re-copies its run into the mirror. `nd db rebuild` empties every table (any schema version) and copies every folder in one transaction, skipping and listing folders it cannot read; `nd db check` compares the database with a copy built from the folders in memory, table by table and run by run.
- **Alternatives:** (D1B) fail the run when the mirror fails: strict, but a database problem would cost hours of training although the master copy is complete; (D2B) an empty `studies` table filled from a meta field nothing writes yet; rewriting a run's rows after every unit: simpler, but on the order of units² rows, and the incremental path would no longer be tested against a rebuild; counting database time in the training clock: the per-unit write is 0.15 ms, but 2–3 ms in a unit with a checkpoint, enough to tip a wall-clock budget.
- **Consequences:** every run trained with `nd train`, `nd sweep` or the runner now also writes `<runs dir>/neurodrive.db` (git-ignored with `runs/`). A database rebuilt from the folders equals the one written unit by unit, also after kills at five moments and resume. The long metrics table is large: the 84 Phase 3–4 folders (78 MB) give 2.38 million metrics rows and a 195 MB database, and a 3,000-epoch toy run takes about 1.4 s longer (0.45 ms per unit) while its training clock and numbers are unchanged. A new schema means a new `DB_VERSION` and a rebuild.

### ADR-039 — Baseline runs: a run folder without training, and without a checkpoint when the baseline is not a network (task 5.6)
- **Status:** accepted (2026-11-02; D1, D2 and D3 chosen by the user: the recommendations A, A, A)
- **Context:** protocol rule 6 requires baselines next to every result, and Phase 5 is done when they have exam cards. A run folder stores a policy as a network checkpoint, but two of the three fixed baselines are not networks: the hand-wired neuron is a `NeuronPolicy` and the scripted expert reads the track.
- **Decision:** (D1A) a baseline is a run folder v1 with no training: budget 0 units, an empty `metrics.jsonl`, status completed, one exam card `exams/unit_0.json`, and a `config.yaml` that describes the policy completely (`experiment/baselines.py`, `baseline_policy(config)` rebuilds it). Methods `random_network`, `hand_neuron`, `scripted_expert`, tag `baseline`. The random network is saved as `checkpoints/unit_0.npz` and its card refers to it (`{"kind": "checkpoint", ...}`); the neuron and the expert have no checkpoint, and their card refers to the baseline (`{"kind": "baseline", "name", "run"}`). (D2A) The random network is examined for seeds 0–9 (one sweep id; median and IQR across seeds); the neuron and the expert are deterministic and get one run each. (D3A) The baseline runs are made in the user's `runs/` too, and the database is rebuilt so it holds every run. Baselines are made with `nd baseline [--name] [--seeds] [--runs-dir]`, outside the runner (which needs a network to checkpoint), and copied into the database mirror.
- **Alternatives:** (D1B) rewrite the neuron as a 7 → 2 network so every baseline has a checkpoint: its fixed throttle would come out of a tanh output as tanh(atanh(0.24)), which may differ from 0.24 in the last bit, and the expert still cannot be a network; (D2B) 5 seeds, the protocol's minimum; (D3B) verify in scratch folders only; a script in `scripts/` instead of a command: later studies must recreate baselines in their own runs folders.
- **Consequences:** a run folder may now have no checkpoint, and an exam card's policy may be a baseline instead of a checkpoint; 5.9's replay must rebuild such a policy from the run's config. The Compare-runs view skips baseline runs (they have no loss), and the toy lab ignores them (not `toy_` methods). The hand-wired neuron's YAML is now read and checked by code (`load_hand_neuron`).
- **Follow-up (2026-11-02, the user's request "create the checkpoints as well"):** D1 is revised for the neuron, which now gets a checkpoint: it is written as a 7 → 2 network with no hidden layer and the neuron's activation on both outputs (steer row: w_left on entry 0, w_right on entry 4, bias b; throttle row: zero weights, bias f⁻¹(throttle), and tanh(atanh(0.24)) = 0.24 exactly), saved as `checkpoints/unit_0.npz`, examined from it, and its card refers to it. The matrix product adds the seven terms in another order than the neuron's two-term sum, so the steering differs from `NeuronPolicy` by at most 9e-16 on 100,000 random observations; over the full exam no episode changes outcome and numbers differ only beyond the 12th digit (progress at most 2.7e-12 m), so the card keeps S1's numbers (training 1.00, held-out 0.25). This was alternative D1B, rejected before it was measured; measured, the difference is in the last bits only. The scripted expert still has no checkpoint: it reads the track and is not a network; a network that drives like it would be a student trained by imitation (Phase 6), a different driver.

### ADR-040 — Random search: fresh candidates, fitness on the training track's exam starts, nd resume (task 5.7)
- **Status:** accepted (2026-11-02; D1 and D2 chosen by the user: the recommendations A, A)
- **Context:** random search is the first driving learner and the null model of every later search method (Phase 7 compares the GA with it at equal environment steps; Study S4 asks whether luck alone beats the baselines). Two choices decide what it measures: what a new candidate is, and on which starts its fitness is measured. It is also the first resumable method, so `nd resume` (moved here by ADR-037) arrives with it.
- **Decision:** (D1A) every candidate is a fresh draw from the initial distribution (Xavier, the learner's own seeded generator): pure random search, selection only; each unit draws `candidates_per_unit` (default 20) networks and keeps the best one so far (strictly better replaces; ties keep the older). The unit-0 network is the learner's first draw, not yet evaluated: with seed k it is the random-network baseline of seed k. (D2A) Fitness is measured on the Driving Exam's 10 starts of a training track (`train_loop_01` by default; held-out tracks are refused by the config, protocol rule 7): per start f = p + c · (1 − t / T) with p the progress as a share of the target laps (in [0, 1]), c = 1 for a finish and t its time, T the time limit; F = mean f, 0 ≤ F < 2. A unit's environment steps are the car-steps driven. The evaluation drives all N · S cars in one world and computes sensors only for running cars (bit-identical readings, about 9× faster for random networks, most of which stop within seconds). Config v1 gains `method: random_search` (§6.15); `nd train` / `nd sweep` pick the method from the file (`--units` overrides `budget.units`); `nd resume --run` rebuilds the learner from the run's config and continues it.
- **Alternatives:** (D1B) a Gaussian nudge of the best so far (hill climbing): faster, but already a (1 + λ) evolution strategy, the subject of Phases 7–8, so S4 would no longer test luck alone; (D2B) 2 starts: 5× cheaper per unit, but a network can win by suiting those two starts; computing sensors for every car (as the episode runner does): 9× slower here.
- **Consequences:** the training-track part of the exam is measured on the same starts the fitness uses, so it is not independent evidence (the held-out tracks are); best-so-far fitness never decreases (fixed, deterministic evaluation). Phase 7.2 can reuse `evaluate` for a GA's population. Resuming works for random search; toy runs still cannot be resumed (ADR-037).

### ADR-041 — api v1.13: launching training runs from the app, following them over /ws/runs, and a stop request in the run folder (task 5.8)
- **Status:** accepted (2026-11-02; D1 and D2 chosen by the user: the recommendations A, A)
- **Context:** Phase 5 is done when random search "trains in the background" and the app shows its progress. §3 planned training in separate processes that only write files, a server that watches them, `POST runs`, `POST runs/{id}/stop` and a `/ws/runs` socket with four event names, but not what the browser may launch, how a run is stopped, how the server learns the id of a run it started, or how the four events look.
- **Decision:** (D1A) the browser launches a config file from `configs/` with the overrides of `nd train` (seed, tag, epochs or units); the server validates them exactly as `nd train` does (422 with the problems, nothing started) and runs `python -m neurodrive train --config configs/<name> … --runs-dir <runs>` as a separate process, so a launched run equals a terminal run (tested folder for folder). `GET /api/configs` lists the files. (D2A) Stop writes an empty file `stop_requested` into the run folder; the runner checks it before each next unit and ends the run cleanly: status `completed`, new stop reason `stopped`, the last unit checkpointed and examined; the request is removed before the final status, and `resume` removes a stale one. It also stops runs started in a terminal. Implementation: the process runs in its own process group (on Windows a new group without a console window), so stopping the server does not stop it; it runs in the runs folder's parent with `--runs-dir <folder name>`, so its log (`<runs dir>/.launches/<time>.log`) holds no absolute path; `nd train` prints `run folder: runs/<id>` as soon as the folder exists (`on_start`), and the server waits up to 60 s for that line; at most 4 launched runs train at once (409). The watcher polls every 0.5 s while a browser is connected, re-reads `meta.json` only when its time or size changed, tails each running run's `metrics.jsonl` by byte offset (complete lines only), lists checkpoints and exam cards before reading the metrics (so a card's line is always sent first), and starts a run's history again (`replace`) when tracking starts or a resume cut the file back. `/ws/runs`: `run_status` to everyone, `metrics` / `checkpoint` / `exam_done` only for the run a connection `watch`es, whose history it receives first from the same in-memory copy, through one ordered queue per connection. The web app gets an Experiment tab "Training". API version **v1.13**.
- **Alternatives:** (D1B) a YAML editor in the browser: anything possible, but the text must be saved somewhere first and errors are easy to type; (D1C) a form for every config field: one form per method, extended by every later method; (D2B) killing the process: immediate and resumable for random search, but toy runs stay half-done, only processes this server started can be stopped, and the folder does not say the stop was intended; (D2C) no stop yet. For following runs: file-system notifications (`watchdog`, a new dependency, unreliable on some disks); the trainer reporting to the server over a socket (training would need a running server, and terminal runs would be invisible); training in a server thread (shares the server's core and memory; a hang would freeze live driving).
- **Consequences:** a stopped run is finished (`nd resume` refuses it), and stopping waits for the current unit (about 3 s for random search, plus its exam). While a run trains, every connected browser gets a `run_status` about every 0.5 s (its unit count changes). The server learns a launched run's id only from the process's first line; a run killed from outside shows as running with an exit code until resumed. Each full browser test run adds two small random-search folders (tags `e2elaunch`, `e2estop`) to `runs/`.

### ADR-042 — api v1.14: a checkpoint is replayed as a live driver from the exam's starts; new bests get checkpoints; the run timeline (task 5.9)
- **Status:** accepted (2026-11-02; D1 and D2 chosen by the user: the recommendations A, A)
- **Context:** Phase 5 is done when the timeline replays any checkpoint with the Network view linked. §3 and §7 planned `POST replay` returning an Episode Recording and a browser "replay mode" that draws from it, but every view (canvas, HUD, trail, Network view, inspector, what-if) is built on the live session's messages. The user also asked to watch the car improve "after each generation", while the runner checkpointed only on the schedule 0, 1, 2, 5, 10, …: a 50-unit random search found new bests at units 1, 6, 7, 16, 19 and 26, and the networks of units 6 and 16 were never saved.
- **Decision:** (D1A) a checkpoint is replayed in the live session: `load_scenario` accepts `policy: "checkpoint"` with `checkpoint {run, unit}`; the session loads the network from the run folder (refusing unknown runs or units, non-driving networks and runs without checkpoints, keeping the old scenario), places 10 cars at the Driving Exam's starts in exam order with the exam's 2 laps, and drives them with one `MLPPolicy` as one batch, so its step loop reproduces the exam drive exactly (every car's status and progress equal the card's to the last digit, tested on two tracks for every checkpoint of a run). `scenario` echoes the checkpoint. `GET runs/{id}/checkpoints/{unit}/diff?from=` returns delta, M = max |delta| and change = delta / M per weight and bias; `GET runs/{id}/exams/{unit}` returns the card. The web app gets an Experiment tab "Timeline" (run, track, checkpoint slider, chart cursor, per-car card results) and Network-view diff colouring (blue up, orange down, strength |change|, unchanged lines hidden; on by default in a replay, against the previous checkpoint). `POST replay` is not built now. (D2A) `UnitResult.new_best` (optional, default false): the runner checkpoints and examines every unit that reports a new best besides the schedule; random search sets it when it improves. API version **v1.14**.
- **Alternatives:** (D1B) `POST replay` + a separate replay mode: instant scrubbing within a drive, but a second data path through every view, no what-if on replays, roughly twice the work; (D2B) the fixed schedule only: improvements between scheduled units stay invisible.
- **Consequences:** a replay offers everything a live network driver does (trace, inspector, what-if, ghost car, trail, looking back), but scrubbing within a drive is limited to the session's 60 s memory, and the replayed drive starts at step 0 on every checkpoint change. For random search the expected number of extra checkpoints and exams is H_n − (scheduled units among them), about 5 per 100 units; a GA (Phase 7) may improve in many early generations, at most one exam per unit. Runs made before 5.9 keep their schedule-only checkpoints. The browser tests train a 3-unit random search (tag `e2e`) once for the timeline test.

### ADR-043 — Studies in the run folders and the mirror: a `study` field in meta.json, db v2 with a derived `studies` table, S4 makes its own baselines (task 5.10)
- **Status:** accepted (2026-11-02; D1, D2 and D3 chosen by the user: the recommendations A, A, A)
- **Context:** ADR-007 planned a `studies` table and ADR-038 moved it to task 5.10 "together with a `study` field in meta.json". Open were what the table holds when the folders are the master copy, how the baselines (made once in 5.6, without a study) belong to a study, and Study S4's budget.
- **Decision:** (D1A) a run made for a study has `"study": "<ID>"` in `meta.json` (letters, digits, `_`, `-`), written by `--study` on `nd train`, `nd sweep` and `nd baseline` or by a study script; runs without it are unchanged. Mirror **db v2**: `runs` gains a `study` column (indexed), and the new table `studies` is *derived* from `runs`: one row per study id with `n_runs`, `methods`, `sweeps`, `git_commits` (sorted JSON lists), `started_at` (earliest) and `ended_at` (latest, empty while any run of the study has none). The row is recomputed whenever a run row of that study is written or deleted, so it never holds anything the folders do not say; rebuild and check treat it like every other table. The question and hypotheses of a study stay in `docs/studies/<ID>.md`. A v1 database is refused with the "rebuild" message (a running run warns and goes on, ADR-038). (D2A) S4 makes its own baseline runs with `study: S4` (random network seeds 0–9, hand-wired neuron, scripted expert); the exam is deterministic, so their cards must equal the 5.6 cards, which the study checks. (D3A) S4 trains `configs/random_search.yaml` for seeds 0–4 (paired with random networks 0–4) at 200 units each (4,000 networks per seed), the five seeds as parallel processes.
- **Alternatives:** (D1B) a study manifest file `runs/studies/<ID>.json` mirrored into `studies`, with the question and a run list: richer rows, but a second kind of record that can list deleted runs or miss added ones (rejected for sweeps in ADR-033 for the same reason); (D2B) runs in several studies (`studies: [...]`, a link table), adding S4 to the 5.6 baselines' meta: no re-exams, but it edits finished master copies; (D3B) seeds 0–9 at 100 units: tighter intervals, half the budget axis; (D3C) seeds 0–4 at 100 units.
- **Consequences:** a new schema means `nd db rebuild` once on every runs folder (the user's was rebuilt in this task). Every later study tags its runs and lists them with one query (`db.runs_of_study`). Baselines are re-made per study (about a minute and a half). The server's run list does not show the study yet (api unchanged).

### ADR-044 — Demonstration datasets (dataset v1): a folder in `data/demos/`, the exam's starts plus seeded random starts, keyboard demos split off (task 6.1)
- **Status:** accepted (2026-11-04; D1 and D3 chosen by the user: the recommendations A, A; D2 chosen by the user: the exam's starts *and* random starts by default)
- **Context:** Phase 6 learns to drive from demonstrations, and task 6.1 records them, but no contract said how a dataset is stored, which frames count towards the demonstration budget, from which starts the expert drives, or how keyboard demos reach the file. Behavioural cloning (6.3), the inspector (6.2), DAgger (6.6) and Study S5c (6.7) all read this format.
- **Decision:** (D1A) a dataset is a folder `data/demos/<YYYYMMDD-HHMMSS>-<teacher>-<tag>/` (git-ignored, ADR-014) with `dataset.npz` (observation (F, 7), label (F, 2), episode, step, and x, y, ψ, v for drawing) and `meta.json` (ARCHITECTURE §6.16). A frame is one car at one step while it was still driving (the steps after a car stopped are left out); `demo_frames` = F = the number of rows. The label has its own column (for a demonstration it is the action driven) so DAgger's relabelled states fit the same format. `learn/supervised/demos.py` holds it; provenance (git commit) is passed in by the caller, since `learn/` may not import `experiment/`. (D2, the user's choice) the expert drives the Driving Exam's 10 starts on a training track **and** `--random-starts N` seeded random starts (default 10, seed 0: arc length uniform on the lap, ±1 m sideways, ±0.1 rad, as the live server's random starts), so the data is not tied to the starts the exam measures; held-out tracks are refused (protocol rule 7); `nd demo-record --teacher expert [--track --random-starts --seed --tag --out-dir]`. (D3A) keyboard recording in the live session (commands, api v1.15, a Record button) is task 6.1b.
- **Alternatives:** (D1B) a run folder in `runs/` with method `demo_record`: listed and mirrored for free, but it is not a training run, and the mirror and every run reader would need a special case; (D1C) one `.npz` with the metadata inside, like a recording: one file, but listing datasets means opening every array file; plain recordings cut into frames at training time: no new format, but every reader repeats the frame rule and relabelled frames do not fit. (D2A, recommended) the exam's starts only by default, random starts as an option; (D2B) random starts only. (D3B) keyboard recording in this task; (D3C) only in 6.7.
- **Consequences:** the default expert dataset on `train_loop_01` has 39,338 frames from 20 finished drives (4.7 MB) and is identical every time; 88 % of its frames steer nearly straight (|steer| < 0.1). Its training-track starts include the exam's, so the exam's training-track part is not independent evidence for cloning either (as for random search, ADR-040); the held-out tracks are. Imitation learners report a dataset's `demo_frames` as their demonstration budget.

### ADR-045 — The dataset inspector: the server reads `data/demos/` directly (api v1.15), the map shows thinned frames coloured by their label (task 6.2)
- **Status:** accepted (2026-11-04; D1 and D2 chosen by the user: the recommendations A, A)
- **Context:** task 6.2 shows demonstration datasets (ADR-044) in the browser: action histograms and the observations covered on a track map. The browser may not compute statistics (ADR-012), so the server has to send them, and no API said how the server finds datasets or what it sends.
- **Decision:** (D1A) `nd serve --datasets-dir` (default `<repo>/data/demos`) gives the server a read-only `DatasetLibrary` (`server/datasets.py`) like the run folders' `RunLibrary`: `GET datasets` lists every folder whose name looks like a dataset id and whose `meta.json` reads, newest first; `GET datasets/{id}` sends the metadata, a 20-bin histogram of each label column and each observation over its fixed contract range (steer and throttle [−1, 1], rays and speed [0, 1], heading error [−1, 1]; the last bin includes the top edge) with min, max and the covered range c = (max − min) / (hi − lo), and the map. The numbers are computed by `experiment/dataset_view.py` (next to `toy_view.py`). 404 for an unknown or malformed id, 400 for a folder that does not load as dataset v1. API version v1.15. (D2A) the map holds every k-th frame, k = ⌈F / 4000⌉, with x, y (2 decimals), steer and throttle label and episode; the browser draws them on the track outline coloured by steer or, switched, by throttle.
- **Alternatives:** (D1B) a `datasets` table in the SQLite mirror (db v3): queries across datasets, but the histograms still come from the arrays, and rebuild and check would need dataset support; (D1C) a `summary.json` written by `nd demo-record` and only served: cheap, but dataset v1 gains a file, older datasets have none, and new bins would mean rewriting every dataset. (D2B) a density grid in track coordinates (arc length × sideways offset): direct about sideways coverage, but an unrolled strip, harder to read at first (a possible later panel); (D2C) every frame (about 40,000 points): no visible difference at map scale.
- **Consequences:** datasets in any folder can be shown (`--datasets-dir`); a large dataset is loaded in full on each detail request (4.7 MB, tens of milliseconds). The browser tests record a small expert dataset tagged `e2e` once. Keyboard datasets (6.1b) and DAgger datasets (6.6) appear without changes, because they use dataset v1.

### ADR-046 — Dense coverage (bins holding at least 1 % of the frames) and a dataset comparator in the inspector (api v1.16, task 6.2 follow-up)
- **Status:** accepted (2026-11-04; D1 and D2 chosen by the user: the recommendations A, A)
- **Context:** the covered range c = (max − min) / (hi − lo) of ADR-045 is set by the two most extreme frames: the expert's left ray "covers 83 %" although 96 % of its frames lie between 0.15 and 0.45 and only 58 between 0.5 and 1. Phase 6 explains a cloned driver's failures by what its dataset lacks (6.5) and compares datasets (DAgger 6.6, keyboard teachers 6.7), which until now meant switching between them.
- **Decision:** (D1A) every histogram also carries the **dense coverage** d: a bin is dense when it holds at least τ·F frames, τ = 1 % (`DENSE_SHARE` in `experiment/dataset_view.py`); d = (summed length of the dense bins, each clipped to [min, max]) / (hi − lo), so d ≤ c. `DatasetHistogram` gains `dense` and `dense_threshold` (= τ·F), api v1.16. The inspector shows "densely covers d (reaches c)", a thick line under the axis over the dense stretches, a thin one over the reach and a dashed line at the share τ. (D2A) a "Compare with" picker adds a second dataset B to the same inspector: two bars per bin (each the share of its own dataset's frames) in the series pair of Compare runs, both datasets' d and c in each caption and the hover, both header lines and episode tables, and on a shared track both point sets on the map, coloured by dataset (default) or by a label on one scale for both (B as rings). No new route: the browser fetches both details.
- **Alternatives:** (D1B) an absolute count, at least 30 frames per bin (one second at 30 Hz): easy to say, but easier to pass the larger the dataset (speed would be 98 % dense from the 120 start-up frames per bin, 0.3 % of the data); (D1C) a quantile range (1st to 99th percentile): one interval, but blind to holes in the middle (the left ray's 2.9 % of frames at exactly 1.0 put its 99th percentile at 1.0). (D2B) two inspectors side by side: nothing new, but charts 300 px apart on different axes and half-width maps; (D2C) a difference view (B's share − A's per bin): exact about change, but hides what each dataset holds; possible later as a switch.
- **Consequences:** on the 6.1a expert dataset d is 30 % for the left ray (c 83 %), 15 % for the right ray (c 45 %), 53 % for speed (c 98 %) and 15 % for steer (c 28 %); the others equal c. τ = 1 % is a judgement call (0.5 % gives nearly the same numbers here) and a very large dataset can have thousands of frames in a bin that is not dense. Clipping makes d exact about the values' extent but still bin-coarse inside it. The browser tests record a second small expert dataset (tag `e2ecmp`) for the comparator.

### ADR-047 — Imitation learner: datasets named by id or newest-of-a-kind and pinned by checksum, validation by whole episodes, and the runner's `checkpoint_every` (task 6.3)
- **Status:** accepted (2026-11-04; D1, D2 and D3 chosen by the user: the recommendations A, A, A)
- **Context:** task 6.3 trains the driving network on a demonstration dataset (behavioural cloning). Datasets are git-ignored (ADR-044), so a committed config cannot name a folder that exists on one machine only; consecutive frames are 1/30 s apart and nearly identical, so the toy learner's random-frame validation split would leak; and Study S5a (6.4) needs a loss and a Driving Exam at every epoch, while the runner checkpoints only on the schedule 0, 1, 2, 5, 10, … and at new bests (ADR-042).
- **Decision:** (D1A) the config's `data.dataset` is a dataset id or a selector `<teacher>-<tag>`, the newest dataset with that teacher and tag (`demos.find_dataset`; `-2`, `-3` suffixes count as newer); `data.sha256` is optional. The runner (`runner.pin_dataset`) finds the dataset in `--datasets-dir` (default `<repo>/data/demos`), refuses it when a given checksum differs, and stores the config with the exact id and the SHA-256 of `dataset.npz`; `meta.json` also gets `dataset` {id, sha256, demo_frames, train_frames, val_episodes}. Training again from a run's `config.yaml`, `nd resume`, and every seed of a sweep therefore use the same frames or refuse. (D2A) validation holds back round(v · E) whole episodes (at least 1, at least one left for training), chosen by a seeded shuffle of the episode numbers (`imitation.episode_split`), v = 0.2 by default. (D3A) `run(..., checkpoint_every=k)` checkpoints and examines every multiple of k besides the schedule and new bests; k is stored in `meta.json` (null by default) and read back by `resume`; the imitation config has the field (`configs/imitation.yaml`: 1). The learner reports the dataset's F frames in unit 1 only (validation frames were recorded too, so they are charged), 0 environment steps and 0 teacher queries. API v1.17: `ConfigInfo.method` may be `imitation`, so the Training tab lists `imitation.yaml`.
- **Alternatives:** (D1B) a recording recipe in the config, each run recording its own dataset (about 20 s): self-contained, but it cannot name a keyboard (6.1b) or DAgger (6.6) dataset; (D1C) as A plus a copy of the dataset in the run folder: self-contained, but 4.7 MB per run and ten identical copies in a 10-seed sweep. (D2B) random frames: every validation frame has a near twin in training, so the validation loss repeats the training loss; (D2C) no validation set: 6.4 could not ask whether a lower validation loss means better driving. (D3B) the learner reporting `new_best` every epoch: no runner change, but the timeline would call every epoch a new best; (D3C) the schedule alone: 8 exams in 100 epochs.
- **Consequences:** a run folder alone does not hold its data: deleting or re-recording a dataset makes a run impossible to repeat or resume (it refuses, it never silently uses other frames). A selector gives a different dataset once a newer one of the same teacher and tag is recorded; the run folder keeps the exact id. Every epoch with an exam costs about 6–20 s of exam against about 0.1 s of training, so `configs/imitation.yaml` (100 epochs) takes about 15–25 minutes. A run launched from the app uses the default datasets folder even when the server was given another (`nd serve --datasets-dir` affects only the inspector).

### ADR-048 — Replays from shifted starts: an optional `start_shift` on the checkpoint and expert drivers (api v1.18, task 6.5)
- **Status:** accepted (2026-11-10; D1, D2 and D3 chosen by the user: the recommendations A, A, A)
- **Context:** Study S5b (6.5) starts S5a's cloned networks from perturbed starts: the exam's starts on the training loop, moved sideways and turned, from which the scripted expert recovers and a clone may not. The roadmap asks for such a crash to be inspected in the Network view, but a checkpoint replay (ADR-042) always started from the exam's own 10 starts, so a perturbed drive could not be opened in the linked views at all.
- **Decision:** (D1A) `load_scenario` takes an optional `start_shift {lateral_m, heading_rad}` (lateral within ±5 m, heading within ±π/2; positive = left), allowed for the `"checkpoint"` driver and for `"expert"`. Every one of the exam's 10 starts is moved by the same shift: start i at its arc length, sideways ℓ_i + δ, heading the road direction + θ, at rest. The starts come from one function, `experiment/exam.py: shifted_starts`, which the study drives too, so a shifted replay ends car for car as the study's drive (tested); shift (0, 0) is the plain replay. With `"expert"` the expert also drives those 10 starts (`n_cars` and `seed` ignored), so the teacher can be watched from the same start. `scenario` echoes `start_shift` (null without one). Any other driver with a shift is refused with `error`, and the loaded scenario stays. API v1.18. The Timeline gets two inputs (sideways metres, heading in degrees, converted to radians before sending) and a "Watch the expert from these starts" button; with a shift it hides the exam card, which describes the unshifted starts. (D2A) S5b drives two networks per S5a seed, the earliest examined epoch that laps the training loop from all 10 starts and the lowest-validation-loss epoch. (D3A) its grid is δ ∈ {−4.5, −3, −1.5, 0, +1.5, +3} m × θ ∈ {−30°, −15°, 0°, +15°, +30°}, from rest, 300 starts per driver.
- **Alternatives:** (D1A′) the same as a separate task 6.5a: cleaner commits, a second Brief/Report round; (D1B) no API change, the crash inspected in Python with `explain/` and drawn as a figure: cheaper, but the linked views could not show it; per-car start lists in the command: any start at all, but the replay would no longer be the exam's starts plus one shift, and the browser would have to build start lists. (D2B) also S5a's training-exam checkpoint (30 networks); (D3B) a smaller grid (120 starts); (D3C) grid A from the expert's planned speed instead of rest: closer to "knocked off line mid-drive", but a second change on top of the position.
- **Consequences:** every S5b crash can be replayed in all three views, and DAgger's networks (6.6, 6.7) can be replayed from the same starts. A shift that puts a car beyond the crash offset (|ℓ_i + δ| > 5 m) ends it at the first step, which the replay shows as an immediate crash. The exam card is not a description of a shifted drive; the study's results file is.

### ADR-049 — DAgger: one round per unit, continued training, fresh random starts, and the collected frames saved as a dataset; teacher queries in the budget (api v1.19, task 6.6)
- **Status:** accepted (2026-11-10; D1, D2, D3 and D4 chosen by the user: the recommendations A, A, A, A)
- **Context:** Studies S5a and S5b found that a behavioural clone fails in states its teacher never visited, and that training it longer makes it a better copy on the teacher's states and a worse guesser everywhere else. DAgger (Ross, Gordon and Bagnell, 2011) collects data where the student goes: the student drives, the teacher labels the states it reaches, the labelled frames are aggregated and the student is retrained. No contract said what one unit of such a learner is, whether it retrains from scratch, from which starts it drives, how its teacher labels are charged, or where its collected frames go.
- **Decision:** (D1A) one unit is one **round**: round 1 is E epochs of behavioural cloning on the dataset (the imitation learner's own epoch, by subclassing, with the same generators, so it equals imitation bit for bit); every later round drives the current network, labels, aggregates and trains E more epochs. The expert mixing is β_1 = 1, β_i = 0 afterwards. (D2A) training **continues** from the current network and the optimizer's state. (D3A) each collection drives R = 10 cars from **fresh seeded random starts** (generator "collect": arc length uniform on the lap, ±1 m, ±0.1 rad, at rest, the dataset's random-start recipe) on a training track, with the per-track rules for 2 laps. A collected frame follows the dataset rule (ADR-044) and is one environment step and one **teacher query**; the expert's label is recorded before each step and never steers (`ExpertLabelled`). The validation set stays the dataset's held-back episodes; each round also reports the collection drive's on-policy error. (D4A) the collected frames are in the learner's saved state (for resume) and, when the run ends, saved as a dataset v1 `<time>-dagger-<tag>` (teacher kind `dagger`) in the datasets folder, named in the run's `meta.json` as `dagger_dataset`. Config `method: dagger` (§6.15), `--units` sets the rounds; API v1.19: `ConfigInfo.method` may be `dagger` with `length_field` `units`.
- **Alternatives:** (D1B) one unit per epoch with a collection every E epochs: finer curves, but 300 exams per run or unexamined epochs; (D2B) a fresh network every round, the paper's version: the network depends only on the data, but each has only E epochs, which mixes S5a's early-versus-late effect into the comparison; (D3B) the demonstrations' full recipe (the exam's starts plus random ones) every round: the exam's training starts re-driven and trained on each round; (D3C) wider random starts: more recovery data, but "DAgger plus perturbed starts", overlapping S5b's test grid; (D4B) the frames only in the run's state: nothing new in `data/demos/`, but the inspector cannot show them.
- **Consequences:** DAgger is the first learner with a non-zero teacher budget, and its environment steps equal its teacher queries. A DAgger run writes into the datasets folder (18–21 MB per 10-round run: 149,000–178,000 frames in task 6.6), so a sweep leaves one dataset per seed; a failed run saves none until it is resumed to its end. Later epochs cost more than early ones, because the aggregated set grows each round, so "the same number of epochs" as a cloning run is not the same number of gradient steps. Its collection starts never include S5b's large shifts, so S5b's grid tests robustness the method was not trained on.

### ADR-050 — DAgger's collection starts get configurable ranges, and the expert recorder too (task 6.6 follow-up)
- **Status:** accepted (2026-11-10; F1A, F2B and F3A chosen by the user; the user chose to follow up 6.6 instead of closing it, after V1 and V2 were not supported)
- **Context:** 6.6's DAgger (ADR-049, D3A) collected from starts moved at most ±1 m and turned at most ±0.1 rad. It copied the expert ten times better than the clones on its own states and no longer collapsed with long training, but finished fewer of Study S5b's 30°-turned starts than S5a's early clones: its own mistakes never produced large heading errors (the DAgger data covered 4.5 % of the heading-error range, the expert's 3.4 %). Whether wider collection starts help, and whether any help is DAgger's or merely the starts', needed a setting and a control.
- **Decision:** (F1A) only the collection starts change. `DaggerSettings` and the config's `dagger` section gain `start_lateral_m` a (0 to 4.5 m) and `start_heading_rad` h (0 to π/4); each collection start is moved sideways uniformly on ±a and turned on ±h. The defaults stay 1.0 and 0.1, so 6.6's runs and configs are unchanged (tested: the defaults give the same collection bit for bit). (F2B) `configs/dagger_wide.yaml` uses a = 3 m, h = 0.35 rad (20°), so the grid's outer cells (±4.5 m, ±30°) stay outside the training range. (F3A) the control is behavioural cloning on an expert dataset recorded from the same wide distribution: `record_expert` and `nd demo-record` gain `--start-lateral` and `--start-heading` (defaults 1 and 0.1); the exam's 10 starts plus 90 wide random starts gave 196,765 frames, about DAgger's demonstrations plus teacher queries. `scripts/check_dagger.py --wide` trains both for seeds 0–4 and scores them on S5b's grid, with checks W1–W3 written before any run.
- **Alternatives:** (F1B) expert mixing β in later rounds: closer to the paper, but the expert also drives near the line, so it hardly widens the heading range; (F1C) both as variants. (F2A) a = 4.5 m, h = 30°: the whole grid inside the training range, a stronger signal but no longer a test of poses never trained from. (F3B) no control: quicker, but a gain could not be credited to DAgger.
- **Consequences:** results (seeds 0–4, recoverable shifted starts): DAgger-wide median 0.836 [IQR 0.789, 0.839], above 6.6's DAgger (0.543) in 4 of 5 seeds and above S5a's early clones (0.725): W1 supported. The wide clone scored 0.764 [0.021, 0.775]; DAgger-wide beat it in 3 of 5 seeds (W2 not supported), with a narrower spread and fewer crashes (0.114 against 0.154). Seed 2's DAgger-wide network collapsed in its last round (training loss 0.013 → 0.027, all 10 exam cars crash at one bend), so W3 (laps the training loop in every seed at round 10) was not supported; its round-9 network finishes 0.754 of the grid (post hoc). The wide data covers about 10 % of the heading-error range, three times the default DAgger data. The wide clone's training-loop laps still flicker from checkpoint to checkpoint; DAgger-wide's are stable from round 5 on, except seed 2's last round. Wide starts make the data's width, not DAgger alone, the main lever; DAgger adds reliability on top. Both of these points are for Study S5c (6.7).

### ADR-051 — Keyboard demonstrations: the live session records one car on a training track from step 0, drives become episodes, and the server saves the dataset (api v1.20, task 6.1b)
- **Status:** accepted (2026-11-11; D1, D2 and D3 chosen by the user: the recommendations A, A, A)
- **Context:** ADR-044 (D3A) left keyboard recording in the live session to task 6.1b, so that Study S5c (6.7) can compare a human teacher with the scripted one. Nothing said which car is recorded, what one recorded drive is, when a file is written, or who writes it. The browser may not compute or store driving (ADR-012), and this is the first time a click in the browser makes the server write a file.
- **Decision:** (D1A) recording is allowed only with the keyboard driver, **one car**, on a **training track** (protocol rule 7), and starts from whatever start the scenario has (the track's fixed start, or the seeded random start; the seed goes in `starts`); otherwise `record_start` is answered with `error` and nothing is recorded. (D2A) one dataset per recording: each drive from step 0 is an **episode** (`start_kind` `live`, its start pose from `World.start`); a drive ends with the car's outcome (`crashed`, `finished`, `stalled`, `timeout`), with a **Reset** or with Save/Stop, in which case its status is `stopped`; a drive with no frames is dropped; nothing is written until **Save** (`record_stop {save: true, tag}`); **Discard** forgets everything; recording can only start at step 0, so every episode can be replayed from its stored start; loading another scenario while recording is refused (save or discard first). A frame is the dataset rule of ADR-044: one step while the car is running, with the observation it saw and the clipped action it was given as the label. (D3A) the live server writes the folder `<time>-keyboard-<tag>` into its own `--datasets-dir` with `save_dataset` and the git commit as provenance; the browser sends only the tag, validated as `nd demo-record` does (letters, digits, `_`, `-`, at most 40), and the server builds the folder name. New commands `record_start` and `record_stop {save, tag}`; new messages `recording {on, episodes, frames}` (sent with every frame while recording, after a reset, and when recording starts or ends) and `dataset_saved {dataset_id, frames, episodes}`; api v1.20. The recorder is `learn/supervised/demos.py: DemoRecorder`, fed by `LiveSession._advance` just before the world moves.
- **Alternatives:** (D1B) several cars, recording the selected one: the keys drive all of them, so the others are meaningless, and the selection can change mid-drive; (D1C) held-out tracks too, flagged: breaks rule 7 for anyone who then trains on the file. (D2B) save automatically after every drive: many tiny datasets to choose among; (D2C) start mid-drive: the first episode has no replayable start. (D3B) the browser downloads the file and the user places it by hand: no write by the server, but the learners cannot use it until it is copied.
- **Consequences:** a keyboard dataset has the same format as the expert's, so the Datasets tab, `data.dataset: keyboard-<tag>` in `configs/imitation.yaml`, and DAgger's `base_dataset` work without change. Its labels take at most nine values (steer and throttle each in {−1, 0, +1}) and follow the person's reaction time, not only the state; this is what S5c will measure. The browser tests save a dataset tagged `e2ekey` into `data/demos/` on every run (git-ignored, like the other e2e datasets). A server started without a datasets folder (`LiveSession` built without one) refuses to record.
